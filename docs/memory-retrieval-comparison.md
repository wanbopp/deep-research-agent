# 企业级记忆检索方式对比

## 概览

| 检索方式 | 核心原理 | 适用规模 | 复杂度 | 典型延迟 |
|---|---|---|---|---|
| 向量相似度检索 | 全量余弦距离排序 | 单用户 < 1K 条 | 低 | 10-50ms |
| ANN 向量索引检索 | HNSW/IVF 近似最近邻 | 单用户 1K-100K 条 | 中 | 1-10ms |
| 混合检索 | 向量 + BM25 关键词融合 | 任意规模 | 中高 | 5-30ms |
| 分层记忆架构 | 按生命周期分级管理 | 任意规模 | 高 | 取决于各层实现 |
| 时间衰减加权检索 | 相似度 × 时间衰减因子 | 任意规模 | 低 | 与底层检索一致 |
| 图谱增强检索 | 知识图谱遍历 + 关系推导 | 关联密集场景 | 高 | 5-50ms |

---

## 1. 向量相似度检索（Exact Search）

### 原理

```
用户输入 → Embedding 模型 → 查询向量
                                ↓
              数据库中所有记忆向量 ← 余弦距离排序 → Top-K 返回
```

### 特点

| 维度 | 说明 |
|---|---|
| **优点** | 语义理解强；实现简单；结果精确（无近似损失） |
| **缺点** | 记忆量大时全量扫描变慢；对精确关键词不敏感 |
| **适用场景** | 单用户记忆量较小（< 1000 条）的早期阶段 |

### SQL 示例（pgvector）

```sql
SELECT id, content, kind,
       embedding <=> $1 AS distance
FROM memories
WHERE user_id = $2
ORDER BY distance, created_at
LIMIT $3;
```

### 当前项目状态

DeepResearch 的 `PostgresMemoryStore.search()` 已实现此方式，使用 `cosine_distance` 对全量记忆做精确排序。

## 2. ANN 向量索引检索（Approximate Nearest Neighbor）

### 原理

```
用户输入 → Embedding 模型 → 查询向量
                                ↓
              向量索引（HNSW/IVF）快速定位候选集 → 精确重排序 → Top-K 返回
```

### 索引类型对比

| 索引类型 | 原理 | 构建成本 | 查询精度 | 内存占用 |
|---|---|---|---|---|
| **HNSW** | 多层跳表图，贪心逼近 | 高（需全量建图） | 高（recall > 0.95） | 高（存图结构） |
| **IVF** | 先聚类到 Voronoi 单元，只搜最近单元 | 中 | 中（依赖 nprobe） | 中 |
| **PQ（乘积量化）** | 高维向量压缩成短码，查表代替距离计算 | 高 | 较低 | 低 |

### pgvector HNSW 示例

```sql
-- 添加 HNSW 索引（一次性操作，记忆量大时执行）
CREATE INDEX ix_memories_embedding_hnsw
    ON memories USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- 查询语句不变，PostgreSQL 自动走索引
SELECT id, content, kind,
       embedding <=> $1 AS distance
FROM memories
WHERE user_id = $2
ORDER BY distance
LIMIT $3;
```

### 特点

| 维度 | 说明 |
|---|---|
| **优点** | 查询速度稳定，不随数据量线性增长；对调用层透明 |
| **缺点** | 构建索引耗时；存在少量近似损失；索引占用额外磁盘和内存 |
| **适用场景** | 单用户记忆量 > 1000 条，或总记忆量 > 10 万条 |

### 企业案例

- ChatGPT Memory、Notion AI 均在百万级记忆量使用 ANN 索引

## 3. 混合检索（Hybrid Search）

### 原理

```
用户查询
  │
  ├─→ 向量检索    → Top-N 语义相关记忆
  │
  ├─→ BM25 全文检索 → Top-N 关键词匹配记忆
  │
  └─→ RRF（Reciprocal Rank Fusion）合并排序 → 返回 Top-K
```

### RRF 融合公式

```
RRF_score(d) = Σ  1 / (k + rank_i(d))

其中 k 为常数（通常取 60），rank_i(d) 为文档 d 在第 i 路检索中的排名。
```

### 特点

| 维度 | 说明 |
|---|---|
| **优点** | 同时捕获语义相似性和精确关键词；对专有名词、版本号等敏感 |
| **缺点** | 需要维护两套索引；融合参数需要调优；实现复杂度较高 |
| **适用场景** | 记忆中包含大量技术术语、产品名、ID 等精确匹配需求 |

### 技术选型

| 方案 | 向量 + 全文支持 | 部署复杂度 |
|---|---|---|
| **Elasticsearch 8.x** | 原生 kNN + BM25 | 中（需 ES 集群） |
| **pgvector + tsvector** | 同一 PostgreSQL 实例 | 低（无额外组件） |
| **Azure AI Search** | 托管服务内置 | 低（SaaS） |
| **Qdrant / Weaviate** | 向量数据库 + 过滤 | 中 |

### 示例场景

```
用户查询："PostgreSQL 14 的性能问题"

纯向量检索可能返回：
  1. "用户讨论过数据库优化"         （语义相关但丢失版本号）
  2. "用户提到 PostgreSQL 配置"     （语义相关但模糊）

混合检索额外返回：
  3. "用户报告 PostgreSQL 14 在大数据量下查询变慢"  （BM25 精确匹配 "PostgreSQL 14"）
```

## 4. 分层记忆架构（Hierarchical Memory）

### 原理

```
┌─────────────────────────────────────────────────┐
│  工作记忆（Working Memory）                      │
│  当前对话上下文，直接注入 prompt                  │
│  检索方式：无（始终在上下文中）                   │
├─────────────────────────────────────────────────┤
│  短期记忆（Short-term Memory）                   │
│  最近几天的记忆，权重随时间衰减                   │
│  检索方式：向量检索 + 时间衰减加权                │
├─────────────────────────────────────────────────┤
│  长期记忆（Long-term Memory）                    │
│  持久化的用户知识                                 │
│  检索方式：向量检索 / ANN / 混合检索              │
├─────────────────────────────────────────────────┤
│  核心记忆（Core Memory）                         │
│  用户最重要的偏好/身份，始终注入 system prompt    │
│  检索方式：无（不检索，硬编码注入）               │
└─────────────────────────────────────────────────┘
```

### 各层对比

| 层级 | 容量 | 生命周期 | 注入方式 | 示例 |
|---|---|---|---|---|
| 工作记忆 | 3-5 轮对话 | 单次会话 | 直接拼入 prompt | 当前对话历史 |
| 短期记忆 | 数十条 | 数天~数周 | 检索后按权重注入 | "昨天提到要买服务器" |
| 长期记忆 | 无上限 | 永久 | 检索后注入 | "用户偏好中文交流" |
| 核心记忆 | 极少量 | 永久 | 始终在 system prompt | "用户名叫小明" |

### 特点

| 维度 | 说明 |
|---|---|
| **优点** | 模拟人类记忆分级；核心信息不丢失；上下文窗口利用率高 |
| **缺点** | 需要设计记忆晋升/降级策略；实现复杂度高 |
| **适用场景** | 长期交互的助手类产品，需要兼顾即时上下文和长期知识 |

### 企业案例

| 产品 | 分层设计 |
|---|---|
| **MemGPT / Letta** | core memory + archival memory + recall memory 三层 |
| **ChatGPT Memory** | 自动提取的长期记忆 + system prompt 固定指令 |
| **Mem0** | 用户级 / 会话级 / Agent 级三层记忆 |

## 5. 时间衰减加权检索（Temporal Decay）

### 原理

```
最终得分 = 语义相似度 × 时间衰减因子

时间衰减因子 = exp(-decay_rate × 距今天数)
```

### 衰减曲线示例

```
衰减因子
1.0 ┤ ●
    │   ●
0.8 ┤     ●
    │       ●
0.6 ┤         ● ●
    │               ●
0.4 ┤                 ● ●
    │                       ●
0.2 ┤                         ● ● ●
    │                               ● ● ● ●
0.0 ┼──────────────────────────────────────────
    0   5   10   15   20   25   30   35   40  天
```

### 不同衰减策略对比

| 策略 | 公式 | 特点 |
|---|---|---|
| **指数衰减** | `exp(-λt)` | 衰减快，近期记忆权重远高于远期 |
| **线性衰减** | `max(0, 1 - t/T)` | 在窗口 T 内均匀衰减，超出后归零 |
| **阶梯衰减** | 按天/周/月分桶 | 实现简单，同桶内记忆权重相同 |

### 特点

| 维度 | 说明 |
|---|---|
| **优点** | 实现简单，可与任何底层检索方式组合；自动淡化过时信息 |
| **缺点** | 衰减参数需要调优；某些"古老但重要"的记忆可能被过度降权 |
| **适用场景** | 用户偏好可能随时间变化的场景（如技术栈迁移、兴趣转移） |

### 与当前项目的关系

DeepResearch 当前的排序逻辑 `distance → created_at → id` 已经隐含了"相似度优先、时间次之"的语义，但尚未做加权融合。未来可以在排序中引入时间衰减因子。

## 6. 图谱增强检索（Graph-augmented Memory）

### 原理

```
用户 → [偏好] → Python
  │                ↓
  │          [常用于] → FastAPI
  │                ↓
  └──[偏好] → PostgreSQL

检索 "用户的技术栈" 时，不仅返回单条记忆，
还能沿图谱推导出 "Python + FastAPI + PostgreSQL" 这个完整组合。
```

### 向量检索 vs 图谱检索

| 维度 | 向量检索 | 图谱检索 |
|---|---|---|
| **能力** | 找到语义相似的单条记忆 | 发现记忆之间的关联和隐含知识 |
| **查询示例** | "用户喜欢什么语言" → "用户偏好 Python" | "用户的技术栈" → Python → FastAPI → PostgreSQL |
| **数据模型** | 扁平的记忆条目 + 向量 | 节点（实体）+ 边（关系） |
| **适合场景** | 独立的知识点检索 | 需要推理关联关系的复杂查询 |

### 特点

| 维度 | 说明 |
|---|---|
| **优点** | 能发现隐含关联；支持多跳推理；记忆结构更自然 |
| **缺点** | 需要额外的图数据库；记忆提取为三元组的成本高；查询延迟不确定 |
| **适用场景** | 知识密集型助手；需要理解实体关系的复杂对话 |

### 企业案例

| 产品 | 图谱应用 |
|---|---|
| **Microsoft Graph + Copilot** | 用户邮件、日历、文档之间的关系图谱 |
| **Google Knowledge Graph** | 实体关系推理增强搜索结果 |

## 演进路线建议（DeepResearch）

```
当前阶段（已实现）                 下一步                        远期
───────────────────────    ──────────────────────────    ──────────────────────────
✅ 单用户向量精确检索        → pgvector HNSW 索引           → 混合检索（BM25 + 向量）
✅ MemoryKind 分类过滤      → 时间衰减加权排序              → 分层记忆（core + long-term）
✅ 来源会话所有权校验        → 记忆去重 / 合并策略           → 图谱增强（Neo4j）
✅ 不可变 MemoryItem 投影    → 记忆重要性评分                → 自动记忆提取（Agent 驱动）
```

### 阶段说明

**当前阶段**：精确余弦排序 + 分类过滤，单用户记忆量 < 1000 条时完全够用。

**下一步**：
- **HNSW 索引**：记忆量增长后添加，查询语句不变，PostgreSQL 自动走索引。
- **时间衰减**：在 `ORDER BY` 中引入 `created_at` 衰减因子，淡化过时记忆。
- **去重/合并**：新记忆写入前检查是否与已有记忆语义重复，避免冗余。

**远期**：
- **混合检索**：引入 PostgreSQL `tsvector` 全文检索，与向量检索做 RRF 融合。
- **分层记忆**：区分核心记忆（始终注入）和长期记忆（按需检索）。
- **图谱增强**：利用已有的 Neo4j 基础设施，将记忆构建为实体-关系图。
